# Background interruption diagnosis and recovery

Locking the screen must not cancel a run. Keep the existing process-lifetime Harness, foreground service and SQLite commit/watch pipeline. Foreground re-entry only refreshes views; it never resubmits input. No remote Host or second scheduler is introduced.

## Design and acceptance

- Keep a bounded conversation-scoped `moose.execution` document (200 events) for response failures, generation restarts and explicit cancellation. Record task ID, phase, timestamp, attempt/retry count, stop reason and sanitized error. The transcript remains the source of final results and keeps older errors beyond the diagnostic window. Never store headers, tokens, request bodies or tool arguments in this document.
- Derive current status from committed `pi.live`, transcript and execution diagnostics. Approval waiting overrides running. A failed attempt followed by successful generation in the same user turn is historical recovery, not a failed current task. Details remain accessible beside the attempt.
- Persist cancellation intent before aborting. Android preserves the first native cancellation reason and time before emitting the bridge event; next launch consumes pending cancellation before scheduling. Distinguish notification stop, budget expiry, handshake timeout, notification permission loss, runtime destruction and unexpected service destruction. Abrupt process death cannot reliably identify an OS reason; report runtime restart without inventing one.
- Use Pi's generation retry checkpoint, explicitly bounded to three retries with 2/4/8 second backoff (30 second delay ceiling). Authentication, quota and cancellation are terminal. Recovery reads committed history/tool results; it does not resume an SSE byte offset. Retain Pi's unsafe tool replay protection, and prevent a model from bypassing it with another mutating call after an unknown outcome. The conversation retains an independent unknown-effect latch across compaction and reopening. Only the explicit “Allow further changes” action clears it; a new user message does not clear it, and the action itself never reruns a tool.
- Committed views drive UI, including after reopening. Diagnostic hooks commit before the provider outcome is classified. No UI callback owns execution or persistence. Terminal outcome remains authoritative even when UI detaches.

## Validation matrix

Use controlled model transport and isolated SQLite/workspaces only. No account authorization or paid inference. Verify exact request counts, one stable submission, durable result/status and unsafe operation count.

1. Real Harness/SQLite: network failure -> retry -> completed, auth failure, exhausted retries, cancellation during generation/backoff, reopen after partial generation and unknown tool execution.
2. Android native controlled probe: lock for five and ten minutes; network transition; forced Doze; process termination/relaunch; Termux freeze with signed real tools. Restore any changed emulator network/idle state afterward.
3. Inspect chat attempt details, recovered styling and current status; compile native Kotlin and export both Hermes bundles.

Emulator results do not establish Xiaomi power-management behavior. Record executed cases and limitations below; never substitute UI detachment tests for actual screen-off testing.

## Task notifications

Android keeps one ongoing notification for the shared execution service. During admitted work it observes committed conversation views to show running, retrying, network retry waiting, or authorization waiting. A single conversation links directly to its chat; multiple active conversations show a count and open Moose without assigning the shared service to the wrong chat. Stop still cancels all tasks, and native stop causes and acknowledgement are unchanged.

After settlement, Moose rereads the final committed view before releasing the service. A changed completed or failed outcome posts one result notification per conversation on the **Task results** channel; overlapping leases are deduplicated. A final authorization error counts as a failed result, while an in-progress permission prompt remains waiting. Cancelled tasks do not alert. Unchanged historical outcomes never alert when reopening or retrying an already-settled request. Each repeat iteration is an admitted execution and may produce a result; sleeping intervals do not hold a service.

Result notifications are suppressed when the native Activity is resumed. Failure text uses fixed categories (credentials, network, usage limit, or generic failure) without copying provider bodies or user content. Tapping a result selects the existing persisted conversation through `moose://conversation/<id>`, including a cold launch; the route never submits a request. Invalid or deleted conversation targets are ignored.

Notifications remain required for Android admission. Denying permission prevents work from starting with an explicit error; losing permission retains native cancellation semantics. Muting the separate Task results channel silences results without changing task persistence. No notification permission or new background guarantee is added on iOS. This feature adds no executor, scheduler, or background wakeup.
